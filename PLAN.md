# План перевода «The SaaS Playbook» на русский язык

**Версия:** 0.1  
**Дата:** 16 ноября 2026  
**Исходник:** `The-SaaS-Playbook-ebook.pdf`, 201 страница, ≈46 000 слов  
**Цель:** качественный русский текст для чтения напарником — по главам, с удобной навигацией и без публичного распространения.

---

## 1. Кратко: что и как делать

**Рекомендуемый формат:**

1. **Markdown — единственный источник правды.** Один файл на крупную главу, подразделы внутри как `##`.
2. **HTML-сайт собирается из Markdown автоматически** (MkDocs Material): оглавление, поиск, мобильная вёрстка, тёмная тема.
3. **EPUB собирается из тех же файлов** — самый удобный формат, чтобы отправить напарнику «почитать» на телефоне, Kindle или в Apple Books.
4. **PDF — только для финальной печати.** Вручную HTML и PDF не редактируем: любая правка делается в Markdown и пересобирается.
5. **GitHub-репозиторий — приватный.** В нём лежит исходник перевода, глоссарий, стильгайд и скрипты сборки. Готовые EPUB/HTML прикладываем к GitHub Release.

**Почему не «просто HTML» и не DOCX:** HTML плохо диффится и его неудобно править вдвоём; DOCX — бинарный формат, в котором конфликты версий почти неизбежны. Markdown даёт построчный diff, ревью через pull request, историю правок и сборку в любой формат одной командой.

**Ориентир по срокам:** 46 000 слов исходника → примерно 52 000–55 000 слов русского текста. При одном переводчике и полноценной редактуре это **8–11 недель**; при команде из двух-трёх человек — **5–7 недель**; при работе по вечерам — **4–5 месяцев**.

**Юридическая рамка:** книга защищена авторским правом, а перевод — производное произведение. Для личного чтения узким кругом это допустимо, но публиковать перевод в открытом доступе, продавать или распространять без разрешения правообладателя нельзя. Поэтому: приватный репозиторий, сайт только по доступу, исходный PDF не коммитим.

## 3. Формат и структура проекта

### 3.1. Сравнение форматов

| Формат | Плюсы | Минусы | Роль в проекте |
|---|---|---|---|
| **Markdown по главам** | Построчный diff, PR-ревью, переносимость, одна команда для сборки | Не «красивая книга» сама по себе | **Источник правды** |
| **HTML-сайт (MkDocs)** | Навигация, поиск, мобильная вёрстка, тёмная тема | Нужна сборка и хостинг | **Чтение в браузере** |
| **EPUB** | Удобно на телефоне/читалке, офлайн, меняется размер шрифта | Не для совместного редактирования | **Отправить напарнику** |
| **PDF** | Привычная фиксированная вёрстка, печать | Плохо правится, «замораживает» макет | **Финальная версия** |
| **DOCX / Google Docs** | Знакомый редактор, комментарии | Бинарный формат, конфликты версий, дрейф от источника | Только как временный формат для внешнего редактора |

### 3.2. Почему один файл на главу, а не на подраздел

- Крупная глава — это 5 000–7 000 слов: достаточно контекста, но ещё можно отревьюить за один заход.
- Внутри главы работают перекрёстные ссылки, повторы и единый голос автора.
- Один pull request = одна глава. Так проще проверять и откатывать.
- Если над книгой работают два переводчика, делим по главам, а не по абзацам: меньше расхождений в терминах и стиле.

Если глава окажется слишком большой для одного PR, делим её на `part-1.md` и `part-2.md` только на время работы, а в `main` держим цельную главу.

### 3.5. Как читатель получает книгу

**Вариант A — самый простой (рекомендую):**

- Репозиторий приватный.
- В GitHub Release лежит `saas-playbook-ru.epub`.
- Напарник скачивает EPUB и читает где удобно. Никакого хостинга, никаких паролей.

**Вариант B — ссылка на сайт:**

- Собираем MkDocs-сайт.
- Хостим на Cloudflare Pages и закрываем Cloudflare Access (вход по e-mail из списка).
- Это даёт поиск, навигацию и обновление «на лету».
- Важно: **GitHub Pages для приватного репозитория не делает сайт приватным.** На бесплатном тарифе приватный репозиторий вообще не может публиковать Pages; на Pro/Team сайт из приватного репозитория будет **публично доступен**. Приватные Pages есть только в GitHub Enterprise Cloud. Поэтому для закрытого чтения GitHub Pages не используем.

**Вариант C — локальная сборка:**

- `mkdocs build` → zip с сайтом → отправить файлом.
- Работает без интернета, но обновлять такую копию неудобно.

## 4. Стиль и терминология

### 4.1. Решения, которые нужно принять до первой главы

| Вопрос | Рекомендация | Альтернатива |
|---|---|---|
| Обращение к читателю | **«вы»** со строчной | «ты» — теплее, но книга сразу становится менее универсальной |
| Буква «ё» | **использовать везде**, где она нормативна | без «ё» — ближе к типографской традиции, но больше двусмысленности |
| Заголовки | **Sentence case**: «Как выстроить ценообразование?» | Title Case — выглядит по-английски |
| Кавычки | **«ёлочки»**, внутри — „лапки“ | прямые кавычки — только в коде |
| Тире | **длинное тире** с пробелами | короткое тире — не по-русски |
| Имена | транслитерация: Роб Уоллинг, Джейсон Коэн | оставлять латиницей — только для компаний и продуктов |
| Компании/продукты | **латиницей**: HubSpot, Basecamp, TinySeed | транслитерация — только если нет устоявшегося написания |
| Термины | первый раз: русский + (английский), далее русский/аббревиатура | только английский — для узких терминов вроде MRR, CAC |
| Числа и деньги | сохраняем исходные значения и валюту, без пересчёта | пересчёт в рубли — только в сноске, если попросит читатель |
| Сноски переводчика | «Прим. пер.» и только по делу | без сносок — если аудитория знает контекст |

**Почему «вы», а не «ты»:** автор говорит с основателем напрямую, но книга — не личный чат. «Вы» сохраняет прямоту и не выглядит панибратски; неформальность передаём короткими фразами, риторическими вопросами и живыми примерами, а не местоимением.

### 4.2. Голос автора

Роб Уоллинг пишет:

- короткими абзацами;
- прямо, без академической воды;
- с самоиронией и сухим юмором;
- от первого лица, с личными историями;
- с большим количеством конкретных цифр и примеров.

**Задача переводчика — сохранить эту интонацию.** Не «облагородить» текст в канцелярит, не добавлять мотивационного пафоса, не сглаживать шутки. Если шутка не переносится буквально — передать смысл, а не слова.

### 4.3. Терминологическая стратегия

- `GLOSSARY.md` — закон проекта. Если термина нет в глоссарии, переводчик предлагает вариант и обновляет глоссарий в том же PR.
- Первое упоминание ключевого термина: **«соответствие продукта рынку (product-market fit, PMF)»**, далее — «PMF».
- Аббревиатуры метрик (MRR, ARR, CAC, LTV, NRR, ARPU, NPS) не переводим в тексте, но расшифровываем при первом упоминании.
- Названия глав и подразделов переводим смыслом, а не калькой. Например, `SaaS Cheat Code` — «чит-код SaaS», а не «секретный код SAS».
- `moat` — «защитный ров (moat)»; метафора важна, не заменяем на «конкурентное преимущество» везде.
- `escape velocity` — «скорость отрыва»; не «вторая космическая скорость».
- `bootstrapping` — «бутстрэппинг»; при первом упоминании — «развитие на собственные средства (bootstrapping)».
- `playbook` — «плейбук»; в названии книги оставляем английское `The SaaS Playbook` и даём русский подзаголовок.

### 4.4. Оформление

- Абзацы сохраняем по смыслу, но не обязательно один к одному: в русском иногда лучше разбить длинное предложение.
- Списки и подзаголовки сохраняем; если в исходнике список внутри абзаца — оформляем маркированным списком.
- Цитаты и эпиграфы переводим; имя автора и источник сохраняем.
- Числа: «1 000», «$10 000», «5%» (без пробела перед `%`), неразрывный пробел между числом и единицей.
- Даты: «15 июня 2023 г.».
- Ссылки: сохраняем URL; в финале проверяем, что они живые.
- Сноски: только переводческие, с пометкой «Прим. пер.». Авторские сноски, если есть, сохраняем как есть.

## 5. Процесс перевода

### 5.1. Роли

| Роль | Что делает | Кто может совмещать |
|---|---|---|
| Переводчик | Черновик, самопроверка, глоссарий | — |
| Редактор | Двуязычная сверка, стиль, термины | Не тот же человек, что переводчик, в идеале |
| Корректор | Орфография, пунктуация, вёрстка | Может быть отдельным проходом |
| Технический редактор | Сборка HTML/EPUB, ссылки, CI | Владелец проекта |
| Владелец проекта | Решения, приёмка, доступы | Ты |

Для маленькой команды минимум: **переводчик + редактор**. Один и тот же человек может сделать черновик и самопроверку, но финальную вычитку должен делать кто-то свежий.

### 5.2. Этапы

| Этап | Что происходит | Результат | Критерий готовности |
|---|---|---|---|
| 0. Подготовка | Решения по стилю, глоссарий, карта страниц, скелет глав | Репозиторий и документы | Можно начинать пилот |
| 1. Пилот | 1 000–1 500 слов: начало введения + один раздел о ценообразовании | 2 файла/фрагмента | Редактор и владелец согласовали голос и термины |
| 2. Черновик | Перевод по главам, обновление глоссария | `status: draft` | Все разделы переведены, TODO закрыты |
| 3. Самопроверка | Сверка с исходником, чтение вслух, цифры и имена | `status: review` | Нет пропусков и явных кальк |
| 4. Двуязычная редактура | Редактор идёт по исходнику и переводу параллельно | Правки в PR | Смысл, цифры, примеры, термины совпадают |
| 5. Языковая редактура | Стиль, ритм, естественность, единый голос | Чистый текст | Не хочется «переписывать всё заново» |
| 6. Корректура и QA | Орфография, пунктуация, ссылки, вёрстка, сборка | `status: done` | Чек-лист ниже пройден |
| 7. Сборка и релиз | EPUB, HTML, тег версии, GitHub Release | `v0.1`, `v0.2`, … | Напарник открыл и прочитал |

### 5.3. Порядок работы

Рекомендую **книжный порядок**, но с пилотом:

1. **Пилот:** введение (первые 1 000 слов) + «Как выстроить ценообразование?».
2. **Каркас:** предисловие, введение, часть I.
3. **Рынок** → **Ценообразование** → **Маркетинг** → **Команда** → **Метрики** → **Мышление**.
4. **Завершение:** послесловие, благодарности, приложение, титул.

Почему так: пилот проверяет голос и самые «терминологичные» места; часть I задаёт понятия; дальше главы идут в естественном порядке, чтобы перекрёстные ссылки и примеры не теряли контекст.

### 5.5. Работа с исходником

- Извлекаем текст с маркерами страниц (`scripts/extract_source.py`), чтобы всегда видеть, откуда абзац.
- Работаем с исходником и переводом рядом: split-screen в редакторе или два окна.
- Не переводим целую книгу «одним промптом». Даже при AI-черновике каждое предложение сверяется с оригиналом.
- Спорные места помечаем `[[? …]]` и выносим в комментарий PR, а не оставляем в тексте.
- Факты, цифры, имена и названия компаний проверяем по исходнику, а не по памяти.
- Если в исходнике ошибка/опечатка — не исправляем молча: фиксируем в `NOTES.md` и решаем, нужна ли сноска.

### 5.6. Использование AI

AI полезен, но не заменяет редактора:

**Можно:**

- извлекать и выравнивать текст;
- делать черновик, который потом полностью вычитывается человеком;
- предлагать термины и проверять единообразие;
- генерировать HTML/EPUB и проверять ссылки;
- делать обратный перевод спорных фрагментов для самопроверки.

**Нельзя:**

- публиковать AI-текст без двуязычной редактуры;
- позволять модели «додумывать» примеры, цифры и цитаты;
- использовать AI как единственного корректора, если читатель не знает английского.

Если AI использовался для черновика, это стоит честно указать в `README.md` — не ради формальности, а чтобы читатель понимал уровень проверки.

## 6. График и трудозатраты

Оценка для 46 000 слов исходника и 52 000–55 000 слов перевода. Нормы взяты реалистичные, не «рекордные».

| Этап | Человеко-дни | При 1 человеке | При 2 людях |
|---|---:|---:|---:|
| Подготовка и пилот | 4–6 | 1 неделя | 1 неделя |
| Черновик | 18–23 | 4–5 недель | 3–4 недели |
| Самопроверка | 8–10 | 2 недели | 1 неделя |
| Двуязычная редактура | 10–12 | 2–3 недели | 2 недели |
| Языковая редактура | 6–8 | 1,5 недели | 1 неделя |
| Корректура и QA | 4–5 | 1 неделя | 1 неделя |
| Сборка и релиз | 2–3 | 3 дня | 3 дня |
| **Итого** | **52–67** | **9–12 недель** | **6–8 недель** |

**Если работаешь по вечерам** (2 часа в день, 5 дней в неделю): 52–67 человеко-дней → примерно **5–6 месяцев**. Это нормально; лучше сразу планировать реалистично, чем выгореть на середине.

**Что можно ускорить:**

- AI-черновик + полная человеческая редактура: минус 30–40% времени на первый проход, но не на редактуру.
- Параллельная работа над главами: два переводчика + один редактор. Риск — расхождение терминов; лечится глоссарием и общим стильгайдом.
- Отказ от отзывов и «Other Works»: минус ≈1 400 слов.

**Что нельзя ускорять:** двуязычную сверку и финальную корректуру. Именно там ловятся перевёрнутые смыслы, потерянные «не», неверные цифры и кальки.

## 7. Контроль качества

### 7.1. Чек-лист главы

**Полнота**

- [ ] Все подразделы из `SOURCE-MAP.md` на месте.
- [ ] Нет пропущенных абзацев, списков, примеров, сносок.
- [ ] Заголовки соответствуют смыслу оригинала.

**Точность**

- [ ] Цифры, проценты, суммы, даты совпадают с исходником.
- [ ] Имена, компании, продукты написаны единообразно.
- [ ] Примеры и истории не искажены.
- [ ] Нет добавленных фактов «от себя».

**Язык**

- [ ] Текст читается вслух без спотыканий.
- [ ] Нет калек и канцелярита.
- [ ] Абзацы не превращены в бесконечные полотна.
- [ ] Юмор и ирония сохранены (или осознанно адаптированы).

**Термины**

- [ ] Все термины совпадают с `GLOSSARY.md`.
- [ ] Новые термины добавлены в глоссарий.
- [ ] Первое упоминание ключевого термина содержит английский оригинал.
- [ ] Аббревиатуры расшифрованы.

**Оформление**

- [ ] Заголовки, списки, цитаты, сноски отформатированы единообразно.
- [ ] «Ёлочки», длинные тире, неразрывные пробелы.
- [ ] Ссылки живые.
- [ ] `mkdocs build --strict` проходит.

### 7.2. Рубрика приёмки

Оцениваем каждый раздел по шкале 1–5:

| Критерий | Что проверяем | Минимум |
|---|---|---|
| Точность | Смысл совпадает с оригиналом | 4 |
| Естественность | Похоже на русскую книгу, а не на перевод | 4 |
| Термины | Единообразие и корректность | 5 |
| Голос | Интонация автора сохранена | 4 |
| Оформление | Вёрстка и метаданные | 5 |

Если хотя бы один критерий ниже минимума — глава возвращается на правку. «4» — это не «идеально», а «можно читать без раздражения».

### 7.3. Автоматические проверки

`scripts/check_translation.py` проверяет:

- остались ли `TODO`, `XXX`, `[[?`;
- совпадает ли количество заголовков с картой;
- нет ли запрещённых вариантов терминов (например, «СААС» вместо «SaaS»);
- нет ли двойных пробелов, прямых кавычек, дефиса вместо тире;
- не слишком ли текст короче/длиннее исходника (ориентир: 1,05–1,25× по словам).

`mkdocs build --strict` ловит битые ссылки и ошибки навигации. CI запускает это на каждый pull request.

## 8. Риски и как их снимать

| Риск | Последствие | Мера |
|---|---|---|
| Авторское право | Публикация перевода без разрешения | Приватный репозиторий, сайт по доступу, не продавать; для широкой публикации — запросить разрешение |
| Кальки и «переводческий язык» | Текст читается тяжело, теряется голос автора | Двуязычная редактура, чтение вслух, запрет на канцелярит |
| Разъезд терминов | Читатель путается, качество падает | Глоссарий + автопроверки + один редактор на все главы |
| Потерянные «не» и цифры | Смысл меняется на противоположный | Сверка цифр и отрицаний, выборочный обратный перевод |
| Оценка сроков занижена | Проект затягивается, мотивация падает | Баты по 5–7 тысяч слов, видимый прогресс, MVP-релиз |
| Ошибки в исходнике | Переводчик «исправляет» факт и ошибается | Фиксировать в `NOTES.md`, не менять молча |
| Битая ссылка/устаревший ресурс | Приложение выглядит небрежно | Проверка ссылок перед релизом |
| Выгорание | Брошенный проект на середине | Реалистичный график, паузы, ранний EPUB для напарника |

## 9. Что нужно решить до старта

1. **Обращение:** «вы» (рекомендую) или «ты».
2. **Буква «ё»:** использовать (рекомендую) или нет.
3. **Объём:** только основной текст или с отзывами, титулом и «Other Works».
4. **Кто переводит и кто редактирует.** Если ты переводишь сам, кто делает двуязычную сверку?
5. **Срок:** полный проект или сначала 3–4 ключевые главы (Введение, Рынок, Ценообразование, Маркетинг).
6. **Как читает напарник:** EPUB (рекомендую), приватный сайт или и то и другое.
7. **Название на русском:** «SaaS-плейбук» / «Плейбук SaaS» / оставить `The SaaS Playbook` с русским подзаголовком.

Пока решения не приняты, в скелетах глав стоит нейтральный вариант: «вы», «ё», полный объём, EPUB + сайт.
